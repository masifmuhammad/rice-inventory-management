- If any plan's "current code" excerpt doesn't match what you find, the tree has
  moved on again. STOP and re-run `improve-animations reconcile` rather than guessing.

## Why these plans exist

These plans came out of an opportunity sweep of `frontend/src`, not a defect
audit. The app already has a coherent motion system — one vocabulary in
`frontend/src/utils/motion.js`, a documented house rule (`bounce: 0` by default,
overshoot reserved for gestures), reduced-motion handling on every spring, and a
deliberate decision not to animate route exits. Nothing here corrects a mistake.
Each plan either applies the existing vocabulary somewhere it was never wired up,
or resolves a place where two comparable surfaces behave differently.

## Recommended order

Run in numeric order. It is sorted by leverage, and it also front-loads the only
plan with real regression surface while the codebase is otherwise untouched.

1. **001** first and on its own. It is the only plan that changes shared markup
   structure, and it is the only one that can break something unrelated (modal body
   scrolling). Verify it on a real phone before starting anything else.
2. **002** and **003** are independent of everything and of each other.
3. **004** and **005** are small and can be done in any order at the end.

## Dependencies

There are none between plans — no two plans touch the same file.

001 changes `ui/Modal.js`, which every other modal renders through, so plans 004
(`TransactionFormModal`) and any future modal work should be re-verified after 001
lands. That is a verification ordering, not a code dependency.

## Shared traps

Three of these plans hit the same underlying issue, called out individually in
each: **Framer Motion writes a complete inline `transform`, which overrides
Tailwind transform classes.**

- 003 — `-translate-x-1/2` on the `BusinessSwitcher` dropdown must move into the
  motion values as `x: '-50%'`.
- 005 — `-translate-y-1/2` on the sidebar rail must be replaced with
  `inset-y-0 my-auto`.

The repo already documents this at `frontend/src/components/ui/PillFilter.js:122-124`.
If an executor reports a component sitting half its own width or height off after a
change, this is why.

## What was deliberately left alone

Recorded so these don't get re-proposed:

- **List rows** in `pages/Products.js` and `pages/Transactions.js` — they re-render
  on every debounced keystroke and filter change. Enter/exit animation here would
  thrash during ordinary searching.
- **`EmptyState` / `ErrorState`** (`ui/States.js`) — same reason; they mount and
  unmount as filters narrow to zero results.
- **Recharts graphs** on the dashboard — functional data being read and compared.
- **Hold-to-confirm** on destructive buttons — the action is already behind an
  explicit confirm modal; adding a 2s hold on top is friction, not safety.
- **Pagination** and **route exit transitions** — both are repeated, deliberate
  actions where any transition adds perceived latency. The route decision is
  documented at `frontend/src/utils/motion.js:44-47`.
